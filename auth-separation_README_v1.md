# Auth Separation Example Spec

This folder contains a complete, technology-agnostic specification set for a system that separates **authentication**, **authorisation**, and **user information** into three independent services. It is designed as a reference implementation of Specification Driven Development: every artefact below is the source of truth from which a working skeleton can be generated by an AI agent or by a human engineer.

The spec set deliberately does not name a target platform, framework, language, or vendor. It describes contracts and behaviour, not implementation. A skeleton built from these specs should compile, mock, and pass its own contract tests on day one, in any sensible technology stack.

---

## Why three services

A single service that handles login, permission decisions, and personal data carries three different risk profiles in one process. Separation is the standard answer:

- **Authentication (AuthN)** proves identity. It owns credentials and produces tokens. It does not know what those tokens are allowed to do.
- **Authorisation (AuthZ)** decides what a proven identity is allowed to do. It owns roles, permissions, and policies. It does not own credentials and never sees them.
- **User Info** owns profile attributes, preferences, and consent state. It does not authenticate and does not authorise; it serves data once a caller has been authenticated and authorised by the other two.

Each service has its own data store, its own deployment, and its own operational owner. A breach of one does not automatically compromise the others. Compliance scope (PCI for credentials, GDPR for personal data, SOC2 for access decisions) is contained within the service that bears the risk.

### Repository layout

The repository carries the monorepo skeleton the spec set expects (`AUTH-001`). The service directories
are deliberately empty of code — the whole point of this repository is that the specification exists
before the implementation does.

| Directory | Holds | State |
|---|---|---|
| `specs/` | The three OpenAPI 3.1 contracts and the AsyncAPI 3.0 event contract. | Populated — the reviewed deliverable. |
| `features/` | Gherkin acceptance criteria: seven feature files, 21 scenarios. | Populated. |
| `services/authn/` | AuthN implementation, generated from `specs/auth-separation_authn-api_v1.yaml`. | Empty by design. |
| `services/authz/` | AuthZ implementation, generated from `specs/auth-separation_authz-api_v1.yaml`. | Empty by design. |
| `services/userinfo/` | User Info implementation, generated from `specs/auth-separation_userinfo-api_v1.yaml`. | Empty by design. |
| `infra/` | Deployment and infrastructure definitions per `auth-separation_deployment-topology_v1.md`. | Empty by design. |
| `docs/` | Project tracking: backlog, decisions, and implementation logs. | Populated. |
| `scripts/`, `vendor/` | Spec-validation tooling and the Kanban's vendored libraries. | Populated, dev-only. |

Each service directory carries a `README.md` stating which contract governs it and which working rules
apply. Ownership is mapped per directory in [`.github/CODEOWNERS`](.github/CODEOWNERS) — which requests
review but only *gates* it once branch protection requires code-owner review.

The OpenAPI files and the AsyncAPI file are the machine-readable contracts. The architecture and README markdown files are human-readable explanations of intent. The Gherkin files are the executable acceptance layer. The three compliance files describe the regulatory scope each service bears: PCI for AuthN, GDPR for User Info, SOC 2 for AuthZ. They sit alongside the API contracts because compliance posture is a property of the service, not a footnote to it.

## How an agent or engineer should use this set

The intended workflow follows the SDD overview (`sdd_overview_v1.docx`) included in this folder. In short:

1. **Read the architecture document first.** It establishes the trust model, the token shape, and the boundaries between services. Without it, the API specs read as three unrelated documents rather than one coherent system.
2. **Generate server stubs and client SDKs from each OpenAPI file.** Use any compliant generator. The generator output is the skeleton; do not edit it by hand.
3. **Generate the event publishers and consumers from the AsyncAPI file.** The events are the only legitimate channel for cross-service state propagation. Do not introduce direct synchronous calls between the three services beyond what the OpenAPI contracts permit.
4. **Implement the business logic behind the generated stubs.** The contract is fixed; what fills the controller methods is not.
5. **Stand up the Gherkin scenarios as the acceptance test suite.** Every scenario must pass before the skeleton is considered production-ready.
6. **Add contract verification in CI.** Each running service must continue to satisfy its OpenAPI definition; drift is a build failure.

## What the spec does and does not cover

### Covered
- HTTP API contracts for all three services
- Token formats and validation rules
- Permission and role data model
- Profile and consent data model
- Cross-service events
- Acceptance criteria for the canonical user journeys
- Error response shapes and status code conventions
- Pagination, filtering, and idempotency conventions

### Out of scope
- Choice of database, runtime, or cloud
- Specific cryptographic libraries (the spec names algorithms, not implementations)
- Rate limiting policies (operational concern, configured per environment)
- UI flows (the spec is for the back-end services only)
- Federated identity provider integration (a future extension; the AuthN spec is structured to allow it without breaking changes)

## Versioning

Every file in this set is versioned independently and the version is encoded in the filename. A breaking change to any contract requires a new major version of that file and a coordinated update to dependent specs. Backwards-compatible additions can be made in place by bumping the spec's internal `info.version` without renaming the file.

## Production-readiness checklist

A skeleton derived from this spec set is considered production-ready when it satisfies every item below. The list is the explicit definition of done for the example.

1. All three services build, run, and respond to health checks.
2. Generated server stubs are wired to real persistence, not in-memory stores.
3. All Gherkin scenarios pass against the running stack.
4. Contract verification (Schemathesis, Dredd, or equivalent) passes against every endpoint in every OpenAPI file.
5. AsyncAPI consumers are running and processing events end-to-end.
6. Tokens are signed with an asymmetric algorithm and keys rotate on a defined schedule.
7. All personally identifiable fields in User Info are encrypted at rest.
8. AuthZ decisions are logged with sufficient detail to reconstruct who was allowed to do what and when.
9. The system has an operational runbook covering credential compromise, permission misconfiguration, and consent withdrawal.
10. Each service is independently deployable with no shared database.

## Validating the specifications

The specifications are machine-checkable today, before any service exists. One command validates all five
machine-readable artefacts and asserts that no secret has been committed alongside them:

```bash
npm ci
npm run verify
```

| Script | Checks | Tool |
|---|---|---|
| `npm run lint:openapi` | The three OpenAPI 3.1 contracts | `@redocly/cli`, `recommended` ruleset |
| `npm run lint:asyncapi` | The AsyncAPI 3.0 event contract | `@asyncapi/parser` |
| `npm run lint:gherkin` | The Gherkin acceptance criteria | `@cucumber/gherkin` |
| `npm run lint:secrets` | Every tracked file, for committed credentials | in-repo, `git ls-files` |
| `npm run lint:kanban` | The Kanban board's status against the backlog | in-repo, dependency-graph derivation |
| `npm run lint:kanban-content` | Ticket content against the decisions that amend it | in-repo, declared-amendment check |

Structural errors fail the gate. Style warnings are reported but tolerated: the specifications are this
project's reviewed deliverable and are not reshaped to satisfy a linter's house style. The same command
runs in CI on every push and pull request. The tooling is dev-only — nothing here ships, and no
implementation language has been chosen.

The Gherkin leg enforces one Feature per file across `features/` and asserts the total scenario count, so
neither a re-bundled file nor a scenario quietly dropped in a refactor can pass. The secrets leg scans
what is actually committed (`git ls-files`) for private key blocks, provider tokens, and `.env` files; its
deliberately narrow scope is recorded in [`docs/adr/0002-committed-secret-guard.md`](docs/adr/0002-committed-secret-guard.md),
and the CI secrets policy it enforces is in [`infra/README.md`](infra/README.md).

Every leg is negative-tested against a deliberately broken copy before it is trusted. A gate that has
never been seen to fail is not known to work.

## Governance

`main` is protected: changes arrive by pull request with the `Validate specifications` check green, and
force-pushes and branch deletion are blocked — which matters here because the first commit being the
specification set alone is this repository's central evidence. Approving reviews are **not** required,
because a single-maintainer repository cannot satisfy that rule without bypassing it; the requirement is
deferred against a recorded trigger in
[`docs/adr/0001-branch-protection-without-required-approvals.md`](docs/adr/0001-branch-protection-without-required-approvals.md).

## Project tracking

Outstanding work lives in [`docs/backlog.md`](docs/backlog.md), which is the source of truth for **status**.
`auth-separation_implementation-kanban_v1.html` remains the source of truth for **ticket content** —
descriptions, acceptance criteria, and the dependency graph behind all 51 tickets.

The board's own status fields are **generated from those two**, not authored: mark a ticket Done in the
backlog, then run

```bash
npm run kanban:sync
```

which recomputes every card's column from the dependency graph — a ticket is Ready only when *all* its
blockers are Done — and recounts the board's summary. `npm run lint:kanban` is the same check in
read-only mode and runs inside `npm run verify`, so the board cannot drift from the backlog unnoticed.
Reasoning in [`docs/adr/0004-kanban-status-is-generated.md`](docs/adr/0004-kanban-status-is-generated.md).
